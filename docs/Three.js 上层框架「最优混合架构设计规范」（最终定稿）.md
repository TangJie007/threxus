# Three\.js 上层框架「最优混合架构设计规范」（最终定稿）

## 0\. 核心结论（全文最重要一句话）

**采用「DI服务管理层 \+ 原生实体层 \+ 轻量ECS组件层 \+ 流水线中间件层」四层混合架构**

绝对不做纯DI、不做纯原生、不做纯ECS。
所有市面上成熟3D编辑器/游戏引擎（Unity/UE/Babylon）全部都是这套混合模式。

**DI 只管「管理者」，永远不管「实体」。**

## 1\. 四层架构总览（唯一最优结构）

从上到下严格分层，每层职责 100% 不重叠

### 第一层：DI 依赖注入层（服务层）

**角色：全局管理器、系统服务、生命周期持有者**

✅ 全部放入 DI 容器（Provider）

- SceneService / RenderService / CameraService

- AssetService / DisposeService / InteractionService

- SerializeService / CommandService / SelectionService

- GizmoService / SnapshotService / ConfigService

- ComponentService（组件调度中心）

- InstancedFoliageService（海量实例管理器）

- AgentBridgeService / HotkeyService / ClipboardService

**特点：**

- 数量少、单例、长期生命周期

- 互相依赖、可注入、可 Mock

- 跟随 Runtime 初始化 \& 销毁

- 可插件插拔（Module/Plugin 模式）

**禁止：存放任何 Mesh、Object3D、实例数据**

### 第二层：原生 Three 实体层（业务对象）

**角色：真实3D物体、场景对象**

✅ **全部不进 DI 容器**

- Mesh / Object3D / Light / Group

- Material / Geometry / Texture

- Gizmo / Helper

**管理规则：**

- 创建：业务代码 / 工厂 Service new / clone

- 增删：统一由 SceneService 托管

- 销毁：统一由 DisposeService 回收

- 依赖：实体可以读取 DI 服务，绝不被 DI 管理

### 第三层：轻量 ECS 组件层（行为逻辑）

**角色：给实体附加动态行为、动画、状态**

✅ 组件是普通 TS 类，**不是 DI Service**

✅ 挂载在 Object3D\.userData

✅ 由 ComponentService 统一每帧调度

适合：旋转、摆动、动画、锁定、可拾取、AI标记

**优点：**

- 同一个模型实例，可挂载不同组件实现差异化

- 不污染原生 Three 类

- 可热插拔、可叠加、可移除

### 第四层：流水线中间件层（横切逻辑）

**角色：拦截、预处理、过滤、校验、埋点**

✅ 全部是纯函数，无状态

分为五条独立流水线：

- Asset 资源加载中间件

- Render 渲染帧中间件

- Interaction 拾取交互中间件

- Serialize 序列化中间件

- Deserialize 反序列化中间件

**边界：业务逻辑绝不写在中间件**

## 2\. 多实例模型的最终标准答案（解决你最大疑惑）

场景：一棵树模型、一百棵树实例、差异化外观、高性能

### 两种实体模式（框架双支持，自动择优）

#### 模式A：普通克隆实体（少量可编辑物体）

**适用：编辑器可选中、可Gizmo、可单独删除的物体**

- 资源 Asset 只加载一次（AssetService 缓存）

- 每棵树 new/clone 独立 Object3D

- 每棵树可单独选中、移动、修改

- DI：实体不进DI，管理逻辑在 SceneService

- 差异化：组件系统控制旋转、摆动、颜色

#### 模式B：GPU实例化实体（海量背景物体）

**适用：森林、草地、数万重复模型、不需要单独编辑**

- 全局只有 **一个 InstancedMesh** JS 对象

- 成千上万个树 = 纯 GPU 实例数据（无JS对象开销）

- 差异化：矩阵随机、颜色随机、偏移随机

- 由 **InstancedFoliageService（DI服务）** 统一管理

**核心哲学：**

重复模型复用「资源」，差异化靠「实例数据/组件」，**绝不靠新建类/新建服务**。

## 3\. 严格边界规范（必须强制执行）

### ✅ 可以进 DI 的

- 系统管理器、全局服务、工厂类

- 生命周期需要统一初始化/销毁的模块

- 需要互相依赖、需要注入、需要 Mock 的逻辑

- 插件模块、配置、事件总线

### ❌ 绝对不能进 DI 的

- Mesh / Object3D / 模型实例

- 几何体、材质、纹理

- 每帧临时上下文 ctx

- 组件 Component 实例

- 中间件函数

- InstancedMesh 的海量实例数据

### ✅ 组件层能做的

- 持有单实体状态、行为、动画参数

- update 驱动实体行为

- 实现个体差异化

### ✅ 中间件能做的

- 拦截、过滤、改写上下文、权限校验、缓存、路径解析

- 无状态、链式、可短路

### ✅ 服务层能做的

所有带「管理、调度、全局、复用、生命周期」的逻辑

## 6\. 框架工具库最终选型规范（适配混合架构）

基于框架**开源、轻量、TS原生、Tree\-Shake、低供应链风险**原则，结合四层混合架构职责边界，统一全局工具库选型，杜绝杂乱依赖、版本冲突、冗余打包体积。

### 6\.1 核心通用工具库（全局唯一替代方案）

#### 主力工具：es\-toolkit（完全替代 Lodash）

**定位：框架唯一基础数据工具库，全局统一使用**

**选型理由**：

- 大厂 Toss 官方持续维护、千万级周下载、社区稳定无停更风险

- 原生 TS 编写，无需外部类型包，类型推导精准，适配框架强类型规范

- 完整 ESM 支持、完美 Tree\-Shake，无冗余打包体积

- 提供 compat 兼容层，完全对齐 Lodash API，兼容老业务代码

- 性能优于 Lodash，体积缩减70%\+，适配浏览器/Tauri双环境

**框架使用规范**：

- 所有服务、插件、工具逻辑，统一使用 `es-toolkit`，禁止引入 Lodash

- 常规业务逻辑使用主入口：`import { debounce, cloneDeep, groupBy } from 'es-toolkit'`

- 兼容旧代码场景使用兼容层：`import { xxx } from 'es-toolkit/compat'`

**禁用替代**：禁止使用 radash/radashi、remeda 等小众库，规避维护中断、社区过小、资料稀缺风险。

### 6\.2 纯TS类型工具库（零运行时体积）

#### 主力工具：type\-fest

**定位：框架专属高级TS类型支持，仅类型导入，无运行代码**

**核心用途**：

- 提供 `DeepPartial`、`Simplify`、`ReadonlyDeep` 等框架必备高级类型

- 适配配置合并、实体类型推导、服务注入类型约束

- 统一全局类型规范，杜绝自定义重复类型

**使用规范**：必须使用 `import type { xxx } from 'type-fest'`，严格仅导入类型，不增加打包体积。

### 6\.3 异步/并发工具库（服务层专属）

仅用于 DI 服务层，处理资源加载、任务调度、中间件流水线异步逻辑，实体/组件层禁止使用。

- **p\-limit**：限制模型/纹理资源加载并发数，防止浏览器请求爆炸，适配 AssetService

- **p\-queue**：带优先级任务队列，用于AI场景生成、批量模型导入调度

**规范**：不引入 radash 内置的并发工具，单独引入轻量化专属包，按需加载、无冗余依赖。

### 6\.4 数据校验库（序列化/AI场景专属）

#### 主力工具：zod

**定位：框架唯一 Schema 校验工具**

**核心用途**：

- 反序列化中间件校验后端/Nest/AI输出的场景JSON

- 运行时 ConfigService 配置校验、参数合法性校验

- 拦截非法脏数据，避免场景渲染报错、崩溃

**禁用替代**：不使用 valibot 等小众替代品，保证生态适配、文档充足、团队上手成本低。

### 6\.5 缓存/数据结构工具（底层服务专属）

#### 主力工具：lru\-cache\-ts

**定位：AssetService 资源缓存专用**

提供标准 LRU 缓存策略，支持过期、最大容量配置，统一框架资源缓存逻辑，不手写缓存算法，规避内存溢出问题。

### 6\.6 工具库分层使用边界（严格匹配四层架构）

|架构层级|允许使用工具|禁止使用工具/行为|
|---|---|---|
|DI服务层|es\-toolkit、type\-fest、zod、p\-limit、p\-queue、lru\-cache\-ts|无限制（按需使用）|
|原生实体层|仅 es\-toolkit 基础数据方法|禁止异步队列、缓存、Schema校验工具|
|轻量组件层|仅 es\-toolkit 简单工具（防抖、浅深拷贝）|禁止复杂异步、缓存、类型工具|
|中间件层|es\-toolkit、zod（仅校验中间件）|禁止任务队列、缓存操作|

### 6\.7 绝对禁用的工具库（框架红线）

- ❌ Lodash：体积大、Tree\-Shake差、类型老旧，全局统一替换为 es\-toolkit

- ❌ radash/radashi：原版停更、社区小、生态弱，不适合开源框架基座

- ❌ effect：架构过重、学习成本高，仅可参考思想，禁止作为项目依赖

- ❌ immer：禁止用于 Three 原生实体对象，仅可少量用于普通配置对象

### 6\.8 工具库选型核心原则

**基座工具大一统，分层使用不越界，轻量无冗余，生态稳长期**。

所有工具库只为「服务层、横切逻辑」服务，不侵入实体、组件核心渲染与业务行为，完美适配整体混合架构规范。
